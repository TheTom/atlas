# Qwen3.8 official FP8 precision audit

Source: Atlas `fd65fb85a09e9ff3d81c36fcbceffff4bdc38269`; checkpoint `Qwen/Qwen3.8-27B-FP8`, revision `017b9c7af6b5689d5dd426a76e0bc077eb5ca20a`. This is a source/retained-log audit, not a claim that the new native profile has executed successfully.

`ATLAS_DENSE_FP8=1` retains the original block-scaled FP8 bytes for attention and dense FFN projections on TP1. It overlays them on still-resident NVFP4 fallback weights. It does not choose the LM-head precision. The flag alone is insufficient to claim checkpoint-native execution at every batch size.

The small multi-row FFN defect is in the ordinary concurrent decode paths, not only speculative verification. `can_forward_km` accepts real NVFP4 fallback weights, then `forward_km` reads them without consulting the FP8 overlay. The narrow repair mirrors the existing M2/M3 guard: when a native BF16/FP8 overlay is installed, the M4–8 entry delegates to the existing format-aware `forward_prefill`. Default NVFP4 behavior stays unchanged. The production dispatch regression covers M4/M5/M8 with valid fallback pointers and asserts that all three projections choose the native kernel and never pass the fallback pointer.

For the checkpoint's BF16 head, the explicit supported override is **`--lm-head-dtype bf16`**. This resolves `skip_lm_head_quantization()` and the log must say `LM head kept as BF16 (skip NVFP4 quantization per model config)`. `--lm-head-dtype fp8` would quantize that BF16 head to per-row FP8; it does not preserve the original head. `ATLAS_DENSE_FP8=1` plus the BF16-head override and the FFN dispatch repair define a separate diagnostic profile; do not silently replace the original recipe or its failed results.

Atlas's W8A16 GEMM expands unscaled E4M3 values exactly to BF16, accumulates each128-wide block with BF16 MMA into FP32, then multiplies the block accumulator by the original FP32-widened scale. The product is not narrowed to BF16 before multiplication. Outputs are BF16. The W8A16 GEMV uses BF16 activations and FP32 arithmetic/scales. Default native attention/GDN prefill dynamically quantizes activations to block FP8 and uses an FP32 scale epilogue. These paths are not one uniform activation precision.

The actual vLLM log selects `FlashInferFp8DeepGEMMDynamicBlockScaledKernel for Fp8LinearMethod` and reports BF16 model dtype, `quantization=fp8`, and `kv_cache_dtype=auto`. Its quantized linear path is dynamic W8A8. Butter `b2029a45` uses original block-FP8 weights with FP32 activations and FP32 accumulation/output (W8A32) in its initial correctness operator, preserving mixed BF16 tensors. Thus the defensible comparison is **same pinned checkpoint weight quantization with disclosed engine arithmetic**, not identical arithmetic or a pure kernel-speed comparison. Atlas's FP8 KV recipe and vLLM's auto/BF16 cache are another material difference to disclose; matching weights alone does not match KV precision.

Retained runtime evidence: `qwen38.atlas.c.lat.c1/serve.log` has48 per-layer `native FP8 GDN` messages and line378 says `LM head quantized to NVFP4 (vocab=248077)`. The earlier generic `PREFILL ONLY` GDN log describes a different branch and cannot establish the native checkpoint's dispatch. `qwen38.vllm.b.lat.c1/serve.log` line23 names its actual block-scaled kernel. The FP8 loader emits per-projection scale-grid/dtype widening at DEBUG level (`weight_map/loaders_fp8.rs:102`). There is no comprehensive per-layer FFN route log in the current source, so absence of NVFP4 kernel names in an ordinary serve log proves nothing.

Next runtime diagnostic, owned by the deployment engineer: record the explicit environment and BF16-head argv; check the head log and48 native GDN loads; execute the same deterministic request at C1 and four simultaneously active sequences with spec OFF; confirm a CUDA kernel trace contains native `w8a16_gemm` for the FFN M4 path, rather than `w4a16_gemv_batch4`. Compare greedy output and, if available, first-step logits under both batches. A format-preserving CPU dispatch test proves selection; the real GPU test still must prove arithmetic and allocation behavior. Do not enable `ATLAS_CUTLASS_NVFP4_*` in this profile: those explicit opt-ins can derive NVFP4 from an FP8 overlay ahead of the normal prefill branch.

Stopping rule: identify all weight-family selection points, distinguish source expectations from observed runtime, demonstrate the bad M4 dispatch before fixing, and hand the focused commit and receipts to the deployment owner. No new GPU work was performed by the audit agent.
