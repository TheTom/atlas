# Qwen3.8 single-H100 vLLM 0.28 capacity compatibility

Implemented local rental adaptation `qwen38-h100-vllm028-capacity512` in the existing `qwen3.8-27b-fp8` / `h100` recipe entry, adding only `--max-num-seqs 512` to argv. The entry declares `revision_and_capacity_adaptation`; its notes identify the runtime and distinguish the adapted command from the original source. The original captured recipe, its source URL/hash, the pre-adaptation catalog and failed first cell remain retained. No remote process or GPU state was changed by this investigation. A fresh deployment and coherency result remain unproven.

The observed failure is a capacity/default mismatch, not failed weight loading. The checkpoint loaded 28.54 GiB successfully; vLLM then reported 38.78 GiB available for KV, 622,688 KV tokens, and 810 Mamba blocks. Its implicit scheduler limit was 1024. Installed `vllm/config/compilation.py:1499-1514` refuses full CUDA graph initialization when max_num_seqs exceeds the Mamba block count; its error is explicit about reducing that limit. The first failed cell's raw command/logs are retained at `remote-results/qwen38.vllm.a.lat.c1/`.

The original H100 recipe snapshot omits max-num-seqs and names the floating `vllm/vllm-openai:qwen38` tag. The campaign copied its argument list correctly and added the intended revision pin. This is not a render typo. The rental substitutes a recorded direct vLLM0.28.0 environment; the official tag was not proved to have that exact version or image digest. Installed `engine/arg_utils.py:2592-2601` chooses max_num_seqs=1024 for non-A100 GPUs with at least70 GiB, including this H100. An omitted flag therefore does not mean256 on this environment.

512 is justified by the existing v0.28/H100 graph ceiling, not by a throughput search or a claim that the official model recipe sets that scheduler value. The installed `config/vllm.py:1936-1945` computes the graph ceiling as min(max_num_seqs*(1+spec_tokens)*2, default_graph_cap), then caps it by max_num_batched_tokens; H100's graph cap is512. Both1024 and512 scheduler limits preserve the observed graph ceiling512 with spec off and batch-token budget8192. The version-pinned [vLLM0.28 engine documentation](https://docs.vllm.ai/en/v0.28.0/configuration/engine_args/#max-cudagraph-capture-size) also documents that cap.

Compared with the observed810 blocks, a fixed512 limit leaves298 blocks of margin and remains32 times larger than the frozen C16 workload. The earlier810 proposal is the largest mathematically admissible value for that one allocation, but was superseded because it leaves no margin for allocation variation. No official captured H100 command or installed scheduler default explicitly sets512; its provenance is the existing graph-cap default plus the observed capacity bound.

The CPU reproduction executes the exact installed capacity-guard body, whose full source-file SHA is retained. Original recipe plus installed implicit1024 fails red;811 also fails against810 blocks;810 passes the guard but is not the chosen deployment profile. The separate512 rental profile passes the guard and preserves graph ceiling512 and C16 eligibility. `profile-original-red.json` and `profile-512-green.json` contain complete command, exit code, stdout and stderr. This proves the guard and profile arithmetic only; a fresh GPU boot and coherency gate must still be observed before treating the repair as successful.

The same missing automatic capacity clamp is tracked in [upstream vLLM issue49064](https://github.com/vllm-project/vllm/issues/49064). That report supports the failure mechanism but does not prove this rental's eventual boot. The current [official Qwen3.8 recipe page](https://recipes.vllm.ai/Qwen/Qwen3.8-27B) has multiple hardware and precision examples; their unrelated memory/quantization/speculative settings were not imported into this profile.

The implemented-entry CPU check (`actual_entry_guard.py`) reads the real catalog entry rather than a separately reconstructed argv. Its known-bad original entry resolves to the inspected v0.28 default of 1024 and exits 1 with the same Mamba-capacity error. After the recipe change, the actual entry selects 512 and exits 0; a copy with 811 exits 1 against the same captured 810-block capacity. `actual-original-red.json`, `actual-512-green.json` and `actual-811-red.json` retain commands, complete stdout/stderr, exit codes, wall time and catalog hashes. The initial test-script key typo is separately retained as `actual-guard-harness-key-error.json`; it is not counted as the known-bad capacity proof.

A structural comparison (`actual-entry-scope-check.json`) proves only one model/SKU entry changed, only args/notes/verdict changed inside it, and the argv delta is exactly the two elements `--max-num-seqs`, `512`. Source URL/hash and all other entries are unchanged. `implemented-actual-entry-dryrun.json` records the real renderer's exit 0, explicit adapted verdict, original source hash, spec off and final `--max-num-seqs 512` serve line.

The guard is the verbatim pure-Python conditional extracted from the installed `compilation.py`, with the complete source-file SHA retained in `installed-compilation-guard.json`. Its input metadata uses the observed block capacity and active full-graph mode. This isolates the actual refusal condition without importing the GPU runtime or pretending the CPU fixture establishes fresh device capacity.
